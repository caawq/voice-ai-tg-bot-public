# voice-ai-tg-bot

Голосовой AI-таск-менеджер в Telegram: надиктовываешь голосовое — бот сам
понимает, что это (событие, задача или цель), записывает, напоминает без
давления и раз в неделю присылает картинку-хронологию недели.

Полное описание продукта — в [`voice-todo-bot-concept.md`](voice-todo-bot-concept.md).

## Статус

Ходячий скелет: бот поднимается и отвечает на `/start`. Без базы и без ИИ —
этот этап нужен только чтобы убедиться, что токен и деплой настроены верно.

## Структура

```
bot/        точка входа и хендлеры Telegram (aiogram 3, async)
db/         модели и миграции               (пусто, следующий шаг)
services/   бизнес-логика без обращений к Telegram API (пусто, следующий шаг)
render/     готовый рендер картинки недели: Jinja2 -> HTML -> Playwright -> PNG
config.py   чтение секретов из окружения / .env
```

Правило слоёв: `services/` ничего не знает про Telegram — туда уходит логика,
в `bot/` остаются только хендлеры и работа с апдейтами.

## Запуск локально

Нужен Python 3.10+.

```bash
python -m venv .venv
# Windows:
.venv\Scripts\activate
# macOS/Linux:
source .venv/bin/activate

pip install -r requirements.txt
```

Секреты — только через `.env` (в git не коммитится):

```bash
cp .env.example .env      # Windows: copy .env.example .env
```

Открой `.env` и вставь токен бота из [@BotFather](https://t.me/BotFather)
в строку `BOT_TOKEN=`. Остальные переменные на этом этапе можно оставить
пустыми — они понадобятся со следующего шага.

Запуск из корня проекта:

```bash
python -m bot.main
```

В логах появится `Бот запущен, начинаю polling` — после этого напиши боту
`/start` в Telegram, он ответит текстом-заглушкой.

## Слой данных

PostgreSQL + SQLAlchemy 2 (async) + Alembic. Две таблицы: `users` и `items`
(события, задачи и цели лежат в одной таблице — читаются они почти всегда
вместе, а форму каждого типа стерегут CHECK-констрейнты).

Два правила, которые не стоит нарушать при доработках:

- **В БД всё время в UTC.** «Сегодня», «вечер» и границы недели считаются из
  `users.timezone` (IANA-строка) в `services/timeframe.py`. Ни один запрос не
  должен опираться на дату сервера.
- **Просрочка не хранится.** У статуса нет значения `overdue`: задача
  просрочена, если `type='task' AND status='pending' AND due_date < сегодня` по
  поясу пользователя. Считается на чтении в `services/items.py` — поэтому не
  может разъехаться с реальностью и не требует ночного cron'а.

Миграции — только через Alembic, `create_all` в проекте нет:

```bash
alembic upgrade head          # накатить
alembic downgrade -1          # откатить один шаг
alembic revision --autogenerate -m "короткое описание"
```

Строка подключения берётся из `DATABASE_URL`. Голые `postgres://` и
`postgresql://`, которые отдают хостинги, приводятся к асинхронному драйверу
автоматически (`config.require_database_url`).

## Запуск через Docker (локальный прод)

Бот и PostgreSQL поднимаются одной командой, без ручной установки Python и
Postgres на хост-машину:

```bash
docker compose up -d --build      # собрать и поднять бота и базу
docker compose logs -f bot        # смотреть логи бота, Ctrl+C — выйти из просмотра
docker compose exec bot alembic upgrade head   # накатить миграции на базу в контейнере
docker compose down               # остановить (данные в базе останутся)
docker compose down -v            # остановить и стереть данные базы
```

`BOT_TOKEN`, `LLM_API_KEY` и остальные секреты бот берёт из `.env` — файл не
попадает ни в образ (см. `.dockerignore`), ни в git. `DATABASE_URL` для
Docker-запуска задавать не нужно: `docker-compose.yml` собирает его сам из
`POSTGRES_USER` / `POSTGRES_PASSWORD` / `POSTGRES_DB` в `.env`, адрес базы
внутри docker-сети — всегда `db` (имя сервиса), а не `localhost`.

## Разбор голосовых

`services/voice_parsing.py` превращает расшифровку в список записей, а
`services/parse_flow.py` держит флоу «Записал: … [Да] [Исправить]». Оба модуля
чистые: ни Telegram, ни базы, ни обращения к системным часам — «сегодня» и
таймзона приходят параметрами. Поэтому они гоняются тестами без бота.

Структуру ответа даёт нативный механизм провайдера, а не просьба «верни JSON»:
strict `json_schema`, либо function calling (`LLM_STRUCTURED_MODE=tools`), если
ваш эндпоинт умеет только его. Провайдер — любой OpenAI-совместимый: OpenAI,
OpenRouter, proxyapi.ru, DeepSeek, локальная модель. Меняются только
`LLM_BASE_URL` и `LLM_MODEL` в `.env`.

Схема гарантирует форму ответа, но не смысл, поэтому после провайдера идёт своя
валидация: событию нужен час, у цели не бывает даты, процент лежит в 0–100.
Всё, что её не прошло, и всё, в чём модель не уверена (`confidence_score` ниже
0.75), **не сохраняется молча** — бот переспрашивает явной формулировкой.

Тесты:

```bash
pip install -r requirements-dev.txt
pytest
```

Проверка на живом провайдере (нужен `LLM_API_KEY` в `.env`):

```bash
python -m services.voice_parsing "напомни завтра в 15 позвонить клиенту и купи корм коту"
```

## Картинка недели

Модуль `render/` уже рабочий и не зависит от бота — принимает обычный dict
с данными недели и отдаёт PNG. Для него нужен браузер Playwright:

```bash
playwright install chromium
python -m render.render_week      # положит sample-light.png и sample-dark.png
```

Если Chromium лежит в нестандартном месте (например, в готовом CI-образе) —
путь задаётся переменной `CHROMIUM_PATH` в `.env`.

## Работа с ветками

`main` — стабильная ветка, напрямую в неё не коммитим. Работа идёт в
`feature/*` и вливается через Pull Request. Коммиты — маленькие, по
законченному куску, в повелительном наклонении (`add`, `fix`, `wire`).
